# IMPORT-07 and scoped retention decision

DEC-03-IMPORT records the requesting user's 2026-10-24 approval to retain reviewed import values/fingerprints without uploading raw source files or introducing automatic disposal. This is a stable, independently deliverable child of DEC-03. Effective for local import implementation now; no production activation or wider retention/recovery policy is approved. Family-wide retention durations, archival, attachment limits, acceptable loss/outage, backup and disposal remain pending under DEC-03.

Source identity hashes the exact bytes on the client, plus kind, verified store, exact business date/inclusive period, source slot, parser version, workbook mapping version and reviewed directory revision. Renaming a file does not create a new identity. Fingerprints are client-computed provenance: because original bytes are not uploaded, the server validates the identity structure/hash against the submitted reviewed snapshot, not the authenticity of an absent original file.

`GET/POST /api/internal/import-history/{store}` is manager-only, optional-D1, no-store and bounded. Lists use exact kind/store/period and cursor pages of ten; a single immutable record can also be read by ID. The server stores validated reviewed values, all hours exceptions/source row numbers, source fingerprints/labels, parser/mapping versions, entered reviewer, generated-workbook filename/hash and optional supersedes ID. It rejects raw file/workbook bodies and credential/unknown payload keys. Workbook hashes are explicitly **reported generated-output metadata**, not proof of an OS save or independent business approval. Raw uploads remain in memory; optional device-cached bytes remain separate from shared history.

The first record ID is deterministic from source identity. DATA-05's atomic create/revision/history transaction makes concurrent duplicate roots conflict instead of duplicating. Unchanged uncertain retries keep one operation ID and return their original result. Original records cannot be updated through this route. Deliberate reprocessing creates a new UUID and links an existing same-store/kind/period parent; earlier snapshots remain intact. Changed source/manual values do not silently overwrite earlier reviewed exports.

The UI distinguishes save to shared history, resume reviewed values for another download, and deliberate reprocessing. It requires reviewed generated output and a preparer before recording history. Resume asks before replacing work, clears acknowledgement and original File controls, and regenerates from preserved values after review; it does not promise byte-identical recreation of an old Excel ZIP. Device repeat downloads still use their exact cached bytes. A reviewed record JSON download preserves context/revision/source lineage without secrets. Failed/unauthorized/unconfigured/conflicting saves retain current inputs. Async context/source checks suppress stale completion; context changes clear prior lists. No service failure is presented as a successful empty history.
