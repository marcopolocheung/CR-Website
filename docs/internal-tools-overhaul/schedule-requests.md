# SCH-01: dated schedule requests

Local implementation only. Manager-only GET/PUT `/api/internal/schedule-requests/{station}` uses the existing optional INTERNAL_DB and DATA-05 atomic records/history primitive. Existing migrations 0001–0003 suffice; no schema, production binding, compatibility date, deployed Worker or KV record changed.

Each station owns one undated `schedule-request` record (`requests-{station}`). Its request list is bounded to 200 entries and 600,000 incoming UTF-8 bytes; reaching capacity requires a future reviewed archival design, never automatic deletion. An absent record is an explicit private empty list; absent binding/old Worker is unavailable. This aggregate serializes approvals within a station so overlapping approved exceptions for one legacy identity cannot race. It is an additive envelope service, not a projection into the future shared personnel tables.

Requests pin DEC-01-v1, inclusive shift-start business dates (at most 366 days), station plus original employee ID and display-name snapshot, original requested time, entered-by label/time, narrative and pending/approved/declined state. Actor labels are manager-entered provenance, not authenticated personal identities. UTC receipt/history timestamps are authoritative server write times. Temporary availability stores sorted nonoverlapping minute ranges; an end beyond 1440 denotes the next day of the same starting shift. Time off owns the entire starting business day. Recurring availability and suspension are untouched. Pending overlaps may coexist; approved overlaps for the same identity/date are rejected rather than assigned an implicit priority.

One mutation appends one pending original or reviews one pending request. Original fields, previous decisions and ordering are immutable; deletion/reopening is rejected. Base revisions protect concurrent editors. Stable operation IDs replay the original authoritative success even after later edits; changed content/actor rejects reuse. A guessed future revision cannot bypass domain validation. Clients validate station/store/envelope/data/revision and canonical acknowledged content before accepting a save. Credentials are only authorization headers and never request data.

## SCH-02: manager entry and review

The scheduler loads the manager-only request source and keeps its panel mounted while switching Schedule/Employee settings or weeks. Managers select an explicit station-local employee ID (names never select an identity), enter the inclusive dates, original request time in the device timezone, entered-by label and original narrative, then save a pending request. Temporary availability supports one daily range in this UI, including an explicit next-day end; the service supports up to eight ranges. Separate pending/approved/declined groups preserve entered/requested/review provenance. Review requires a manager-entered reviewer label; approved overlap is explained and rejected. Decisions are final and originals cannot be edited.

English/Spanish request controls switch without remounting or losing fields. The request panel uses the shared dictionaries and language preference; the rest of the scheduler retains its existing language pending SCH-07. Frequent controls are at least 44px with 16px fields. Private requests and reasons are hidden from print and public schedule output. Credentials remain in the scheduler gate's memory and request headers. Request fields remain in session memory, not device storage; existing link/unload protection warns before abandoning them. No device-draft persistence is claimed.

A failed save freezes its exact attempt (including operation ID/base/timestamps). Retry sends that same body. Explicit reload resolves the attempt while preserving unsaved entry/review text; if an appended ID is already saved it clears that acknowledged entry. Concurrent-review conflicts retain both narratives and require comparing reloaded decisions. Missing capability remains distinct from a configured-service failure; neither is presented as empty saved data.

No staff observation, publication or deployment is claimed. SCH-03 applies approved exceptions; this PR only manages request records.

## SCH-03: approved exceptions in scheduling

Only approved requests change scheduling; pending and declined requests never do. For the displayed week, each approved request becomes a dated availability override for the requested employee ID: time off removes that business date, temporary availability replaces that date's hours with the approved ranges (narrowing or widening recurring availability). The derived staff list feeds generation, readiness, independent manual validation, dropdown reasons, drag previews and guided fixes; the saved staff list, published weeks and print output are unchanged. `isEmployeeAvailableForSlot` now honours the slot date, so existing `availabilityOverrides` are respected by both solver and validator.

Suspension remains a separate, earlier check with its own message; an approved time-off message names the request date instead. Empty coverage reports the existing actionable "nobody can work" readiness warning. A kept (locked) spot that conflicts with a new approval returns the existing "no longer fits the rules" diagnostic instead of silently moving the person. If request data is unconfirmed (failed or uncertain load), Make schedule warns that a recent approval may be missing and to reload first.

Local SCH-03 evidence: `npm run scheduler:test` 129 pass (new scenario test covers approved vs pending/declined on identical shifts, narrowing/widening ranges, other-week isolation, coverage warning, suspension separation and kept-spot conflict); `npm run scheduler:requests:test` 5 pass; `NEXT_PUBLIC_SCHEDULE_API=http://127.0.0.1:8791 npm run build`, types and SEO pass; `scripts/test-schedule-requests.py` and `scripts/test-scheduler-views.py` pass against loopback. Scheduler-wide Spanish remains SCH-07; the only changed visible copy outside the request panel is English, matching the existing scheduler. No deployment.
